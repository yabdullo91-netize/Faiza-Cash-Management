Объект: текущее рабочее дерево `faiza-cash`  
Итоговый статус: **NOT READY**

## 1. Краткое заключение

Проект собирается, базовые денежные правила реализованы аккуратно, а основной последовательный набор unit/integration/security-тестов проходит на отдельной PostgreSQL test-базе. Тем не менее проект нельзя считать полностью завершённым или готовым к эксплуатации.

Подтверждены блокирующие проблемы: обход изоляции касс через URL с завершающим слешем; проведение черновика без проверки версии, которую подтвердил пользователь; небезопасная для production конфигурация TLS/refresh-cookie; недостаточная защита финансовой модели ограничениями БД. Дополнительно отдельный catalog-набор дал 9 фактических ошибок из 85 проверок, а заявленный regression-набор целостности проводок является незавершённой заглушкой.

Исходный код, миграции и данные в ходе аудита не изменялись. Созданы только этот отчёт и `FINAL_FIX_PLAN.md`. Существовавшие до аудита незакоммиченные изменения сохранены.

## 3. Подтверждённые проблемы

### FG-001 — Обход изоляции касс через завершающий слеш

- **Критичность:** High
- **Место:** `backend/src/FaizaCash.Api/Middleware/AccessMiddleware.cs:27-31`; `backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:101,117-125`
- **Описание:** защита списков сравнивает путь точной строкой `/api/operations` или `/api/cashboxes`. ASP.NET Core сопоставляет endpoint и для URL с завершающим `/`, но middleware в таком случае не включает обязательный фильтр.
- **Как подтвердить:** войти не-администратором с доступом только к одной кассе; сравнить `GET /api/operations` и `GET /api/operations/` без `cashboxId`, затем `GET /api/cashboxes` и `/api/cashboxes/`.
- **Последствия:** чтение операций, авторов, сумм и списка чужих касс.
- **Решение:** применять ограничение разрешённых `CashboxId` в самих LINQ-запросах/общем authorization service; middleware оставить дополнительным барьером, а не единственной защитой.
- **Приоритет:** P0.

### FG-002 — Проведение не связано с версией, подтверждённой пользователем

- **Критичность:** High
- **Место:** `frontend/src/app/App.jsx:93`; `backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:159`; `backend/src/FaizaCash.Infrastructure/Services/LedgerService.cs:7-19,30`
- **Описание:** PATCH/DELETE проверяют `Version`, но POST `/operations/{id}/post` принимает только id. После открытия подтверждения другой пользователь может изменить черновик, и первый пользователь проведёт уже другие реквизиты.
- **Как подтвердить:** сеанс A читает draft v1; сеанс B меняет его на v2; A проводит по id. Сейчас сервер проводит v2 вместо ответа 409.
- **Последствия:** необратимое проведение суммы или реквизитов, которые пользователь не подтверждал.
- **Решение:** принимать `expectedVersion`, сравнивать её под `FOR UPDATE`, при несовпадении возвращать 409 и требовать повторного просмотра.
- **Приоритет:** P0.

### FG-003 — Production/TLS-конфигурация допускает refresh-cookie без Secure

- **Критичность:** High
- **Место:** `docker-compose.yml:24`; `backend/src/FaizaCash.Api/Program.cs:41`; `backend/src/FaizaCash.Infrastructure/Identity/IdentityServices.cs:13`; `frontend/nginx.conf:10-14`
- **Описание:** Compose запускает API с `ASPNETCORE_ENVIRONMENT=Development`, поэтому HTTPS redirection/HSTS отключены. Refresh-cookie по умолчанию `Secure=false` и становится Secure только при `Request.IsHttps`; forwarded headers не настраиваются, хотя nginx передаёт `X-Forwarded-Proto`.
- **Как подтвердить:** развернуть за TLS-терминирующим reverse proxy и проверить `Set-Cookie`; при текущем pipeline внутренний HTTP может оставить cookie без `Secure`.
- **Последствия:** снижение защиты долгоживущего refresh-token; конфигурация не соответствует production-ready развёртыванию.
- **Решение:** отдельный production compose/override, `Production`, `UseForwardedHeaders` с доверенными proxy, принудительный `Secure=true` вне локальной разработки, TLS на внешнем контуре.
- **Приоритет:** P0 до внешнего развёртывания.

### FG-004 — Финансовая схема не обеспечивает полную ссылочную и статусную целостность

- **Критичность:** High
- **Место:** `backend/src/FaizaCash.Infrastructure/Persistence/CashDb.cs:28-34`; `backend/src/FaizaCash.Infrastructure/Migrations/20261112052646_InitialLedger.cs:34-43,229-275`
- **Описание:** в миграции отсутствуют существенные FK для `Operations.CashboxId`, `DocumentTypeId`, `ReversalOfId`, `ReversalId`, `PostedBy`, а также для ключей `CashAccess`. Нет CHECK для допустимого `Status` и обязательных полей проведённого документа.
- **Как подтвердить:** на копии БД попытаться вставить операцию с несуществующей кассой/пользователем либо `posted` без номера и `PostedAt`; схема принимает часть таких состояний.
- **Последствия:** повреждение регистра обходным скриптом, будущим endpoint или ошибкой приложения; отчёты могут стать несогласованными.
- **Решение:** аудит существующих данных, затем явные EF relationships, FK и CHECK-инварианты; миграцию применять сначала к восстановленной копии.
- **Приоритет:** P0/P1.

### FG-005 — NUL-символы приводят к HTTP 500 вместо контролируемой валидации

- **Критичность:** Medium
- **Место:** `backend/src/FaizaCash.Api/Controllers/DirectoryEndpoints.cs:9-12,32-38`; `backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:112-115`; `.runtime/catalog-test-results.json`
- **Описание:** catalog-набор воспроизвёл 500 для NUL в поиске категорий/контрагентов, названии, контакте и коде типа документа.
- **Как подтвердить:** запустить `node tests/catalog.mjs`; ошибки воспроизводятся для `%00` и строк с `\0`.
- **Последствия:** некорректный клиентский контракт, шум в логах, удобный источник 500-ошибок.
- **Решение:** единая boundary-валидация управляющих символов до EF/Npgsql; возвращать 400 с безопасным сообщением.
- **Приоритет:** P1.

### FG-006 — Дубликаты типов документов разрешены

### FG-013 — `BalanceLimit` хранится, но бизнес-правило не работает

### FG-014 — Экспорты и некоторые отчёты читают неограниченный объём в память

### FG-015 — Отчёт может сочетать данные разных моментов времени

- **Критичность:** Medium
- **Место:** `backend/src/FaizaCash.Api/Controllers/ReportEndpoints.cs:33-41,45-54,59-65`
- **Описание:** opening, rows и totals читаются отдельными запросами без общей snapshot-транзакции. Параллельное проведение между запросами может дать несогласованный отчёт.
- **Как подтвердить:** конкурентный тест с паузой/барьером между запросами и проведением операции.
- **Последствия:** строка, итог и остаток в одном ответе могут относиться к разным срезам.
- **Решение:** `RepeatableRead`/эквивалентный согласованный snapshot либо единый SQL; тестировать конкурентно.
- **Приоритет:** P1.

### FG-016 — Повторная печать исторического документа меняет реквизиты

## 4. Архитектура и положительные свойства

- Разделение Domain/Application/Infrastructure/Api уместно для масштаба; микросервисы не нужны.
- Денежные суммы используют `decimal`/`numeric(18,2)`, JSON сериализует их строками, запрещены ноль, отрицательные и доли копейки.
- Проведение блокирует документ и кассу, проверяет хронологический неотрицательный остаток, создаёт уникальный номер и выполняется в транзакции вместе с аудитом.
- Повторное проведение и совместный перерасход покрыты реальными PostgreSQL integration-тестами.
- Проведённые документы и аудит защищены PostgreSQL triggers от изменения/удаления.
- Refresh-token хранится хешированным, ротируется; reuse отзывает цепочку. Пароли — PBKDF2-SHA512 с индивидуальной солью и 600 000 итераций.
- SQL-интерполяция EF параметризована; прямой string-concatenated SQL и `dangerouslySetInnerHTML` не обнаружены.
- CSV защищает формулоподобные значения; PDF и многостраничный отчёт проверены integration-набором.
- UI имеет светлую/тёмную темы, responsive breakpoints, reduced-motion, loading/error/empty states и доступные подписи основных элементов. Эти свойства не заменяют E2E/ручную доступность.

Архитектурный долг: `ApiEndpoints.cs` концентрирует много функций и однострочных обработчиков; прямое использование `CashDb` размывает границы application layer. Это ухудшает сопровождение, но само по себе не является причиной статуса NOT READY. Разделять следует по вертикальным функциям вместе с тестами, не общим переписыванием.

### Оставшиеся решения, риски и release gate

1. Владелец/руководитель должен утвердить объём смен, отдельного начального остатка, смысл кассового лимита и требования к неизменной исторической печати. Это блокирует полное закрытие FG-012/013/016/018.
2. Требуются полный авторизованный браузерный сценарий для всех пяти ролей и двух касс, обе темы, viewport-матрица, dialogs/focus/keyboard/accessibility; ручной NVDA/VoiceOver остаётся непроверенным.
3. Требуются тест публичного TLS-сертификата и внешнего reverse proxy, нагрузочная проверка/EXPLAIN ANALYZE и отдельный dependency advisory scan. Локальный Compose-конфиг или локальная TLS-проверка не доказывают production readiness.
4. Integrity-миграция остановится до DDL, если read-only preflight находит несовместимые данные; нельзя удалять финансовые строки для обхода ошибки. Перед применением нужен проверенный backup и та же миграция на восстановленной копии.
5. `Down` удаляет ограничения и вычисляемую колонку `NormalizedCode`, а часть старых связей восстанавливает с прежним каскадным поведением. Откат схемы допускается только после репетиции на копии и подтверждённого backup; безопасный первый шаг — откатить приложение, не выполнять `Down` на production автоматически.

Итог: **NOT READY** до согласования требований и завершения перечисленного release gate.
