# План устранения проблем «Фаиза Голд»

План относится к проблемам FG-001–FG-020 из `FINAL_AUDIT_REPORT.md`. Изменения следует выполнять небольшими независимыми группами; после каждой группы — сборка, целевые regression-тесты и проверка миграций на отдельной БД.

## Этап 0 — Зафиксировать критерии приёмки

1. Утвердить обязательность кассовых смен, начального остатка, кассового лимита и исторически неизменной печати.
2. Разделить конфигурации local/test/production и определить поддерживаемую схему TLS/reverse proxy.
3. Зафиксировать тестовую матрицу ролей: admin, accountant, cashier, manager, auditor; минимум две кассы с разными назначениями.
4. Запретить выпуск, пока P0-набор не зелёный.

## Этап 1 — Закрыть изоляцию касс (FG-001)

1. Перенести cashbox-scope в запросы endpoints или общий `ICashboxAuthorizationQuery`.
2. Для не-admin всегда пересекать запрошенный `CashboxId` с `CashAccess`; списки без id не должны становиться глобальными.
3. Добавить тесты для URL с/без `/`, регистра, query string, прямого id, document PDF, reports, analytics и summary.
4. Проверить, что admin сохраняет глобальный доступ, остальные роли не видят чужие данные.

Критерий готовности: ни один вариант маршрута не раскрывает чужую кассу; тесты запускаются в CI.

## Этап 2 — Связать проведение с подтверждённой версией (FG-002)

1. Добавить DTO проведения с `expectedVersion`.
2. Передавать версию из dialog подтверждения.
3. В `LedgerService.Post` сравнить версию после `FOR UPDATE`; при расхождении вернуть 409 без изменений.
4. Добавить конкурентный тест двух сеансов и UI-сценарий повторного подтверждения.

Критерий готовности: устаревшее подтверждение никогда не проводит изменённый документ.

## Этап 3 — Усилить схему БД (FG-004)

1. На восстановленной копии выполнить запросы поиска orphan rows и недопустимых status/posted-реквизитов.
2. Явно описать relationships для Cashbox, DocumentType, reversal links, PostedBy и CashAccess.
3. Добавить FK с осознанными `ON DELETE` правилами; финансовые ссылки по умолчанию `RESTRICT`.
4. Добавить CHECK для `Status`, posted-инвариантов и допустимых значений справочников.
5. Проверить миграцию вверх/вниз и восстановление backup; production данные не исправлять автоматически без отчёта.

Критерий готовности: БД отклоняет orphan и некорректные posted-состояния, допустимые workflows проходят.

## Этап 4 — Production security и deployment (FG-003, FG-019)

1. Создать production compose/manifest с `Production`, без публикации БД наружу.
2. Настроить trusted forwarded headers до HTTPS middleware.
3. Принудительно выставлять refresh-cookie `Secure`, `HttpOnly`, подходящий `SameSite` в production.
4. Вынести миграции в отдельный deployment job; runtime-роль лишить DDL-прав.
5. Добавить smoke-тест TLS, HSTS, security headers, Origin/CORS и `Set-Cookie` через реальный reverse proxy.

Критерий готовности: внешний HTTPS-запрос создаёт только Secure-cookie; API стартует с DML-only ролью после migration job.

## Этап 5 — Исправить каталог и boundary-валидацию (FG-005–FG-007)

1. Ввести общий валидатор пользовательских строк: длина, пробельная нормализация, запрет NUL/опасных control chars.
2. Валидировать `type` фильтров как enum.
3. Добавить уникальный нормализованный code для DocumentType и корректный 409.
4. Проверить аналогичные поля пользователей, касс, организации, поиска и отчётов.
5. Добиться `85/85` в `tests/catalog.mjs` без ослабления ожиданий.

Критерий готовности: никакой проверенный некорректный ввод не даёт 500; дубликаты не сохраняются.

## Этап 6 — Завершить финансовую regression-защиту (FG-008, FG-009, FG-015)

1. Реализовать `runRegressions` в `ledger-integrity.mjs`; убрать unconditional throw.
2. Покрыть backdated posting, одновременные расходы, повторное проведение, сторно, document counter, audit rollback и snapshot отчёта.
3. Сравнивать полный канонический payload идемпотентности, включая `DocumentTypeId`.
4. Выполнять формирование отчёта в согласованном snapshot или одном SQL.
5. Включить ledger/catalog/frontend/build в общий последовательный runner.

Критерий готовности: один CI-командный вход запускает все наборы и падает при любом пропущенном/проваленном обязательном тесте.

## Этап 7 — Закрыть управление доступом и аудит (FG-010, FG-011, FG-017)

1. Добавить выдачу и отзыв доступа как отдельные application commands.
2. Сделать DELETE идемпотентным и защищённым admin policy.
3. Записывать атомарные события `access_granted`, `access_revoked`, `cashbox_limit_changed` с before/after.
4. Добавить UI со списком текущих назначений и явным подтверждением отзыва.
5. Тестировать немедленное прекращение доступа при уже выданном JWT.

Критерий готовности: по журналу однозначно видны актор, пользователь, касса и изменение; отозванный доступ действует немедленно.

## Этап 8 — Принять решение по незавершённой модели (FG-012, FG-013, FG-018)

### Если смены обязательны

1. Реализовать open/close/reopen policy, связь операций со сменой, запрет записи в закрытый период.
2. Сверять расчётный и фактический остаток, фиксировать расхождение и аудит.
3. Добавить UI и конкурентные тесты.

### Если начальный остаток обязателен

1. Добавить одноразовую безопасную команду с датой начала учёта.
2. Запретить конфликтующие исторические операции и последующее изменение без специальной процедуры.
3. Унифицировать формулы Balance/Report opening.

### Если лимит обязателен

1. Определить: hard limit или warning.
2. Проверять его под той же блокировкой кассы, что и проведение.
3. Валидировать PATCH: отрицательное значение → 400, очистка → явный контракт.

Если функции не входят в утверждённый объём, убрать их обещания из SRS/UI/API; физическое удаление таблиц выполнять только отдельной безопасной миграцией после проверки данных.

## Этап 9 — Производительность и историческая печать (FG-014, FG-016)

1. Перенести summary aggregates в SQL.
2. Сделать CSV streaming; для больших PDF — лимит или background job.
3. Добавить максимальный период/число строк и понятный 413/422.
4. Провести нагрузку на реалистичном наборе и `EXPLAIN ANALYZE` до добавления индексов.
5. Если нормативно нужна неизменная печать, сохранять snapshot реквизитов при posted и печатать его.

Критерий готовности: определены SLO и безопасный предел экспорта; исторический PDF соответствует утверждённой политике.

## Этап 10 — Полная UI/UX и accessibility-приёмка (FG-020)

1. Добавить Playwright/Cypress E2E с реальным API и PostgreSQL test-базой.
2. Проверить все роли и страницы: loading, empty, validation, 401/403/409/500, success, длинные строки и большие суммы.
3. Viewport: 320/390/768/1024/1440+, zoom 200% и 400%, светлая/тёмная темы, print.
4. Axe + ручная клавиатура: порядок фокуса, trap/restore в dialog, Escape, skip-link, таблицы, status/live regions.
5. Ручная проверка NVDA/VoiceOver минимум для login, создания, проведения, сторно, отчёта и управления доступом.

Критерий готовности: нет блокирующих WCAG 2.2 AA дефектов; сценарии подтверждены артефактами CI.

## Этап 11 — Backup/restore и финальный release gate

1. Создать backup выделенной pre-production БД.
2. Восстановить в новую пустую БД совместимой версии PostgreSQL.
3. Сверить counts, signed totals, audit, document sequences, пользователей/роли и миграции.
4. Запустить весь CI против восстановленной базы и вручную войти/создать/провести/сторнировать/экспортировать.
5. Провести dependency advisory scan и проверить лицензии.
6. Зафиксировать runbook rollback, RPO/RTO, владельца backup и расписание проверки восстановления.

## Финальный обязательный gate

Релиз допускается только если одновременно выполнено:

- все P0/P1 проблемы закрыты или официально исключены из утверждённого объёма;
- build без ошибок и предупреждений;
- unit, integration, security, catalog, ledger, frontend и E2E тесты зелёные, без обязательных skip;
- production TLS/cookie и role isolation проверены через реальный reverse proxy;
- миграция и restore проверены на отдельной БД;
- финансовые totals и конкурентные сценарии подтверждены;
- повторный независимый аудит не находит Critical/High дефектов.

До выполнения этого gate статус остаётся **NOT READY**.
