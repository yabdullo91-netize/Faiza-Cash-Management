# Три уровня тестирования Faiza Cash

Все команды выполняются из `faiza-cash`. Полный запуск: `node tests/run-all.mjs`.

После доработки интерфейса: 19 unit-тестов, 21 integration-проверка и 12 security-проверок. Дополнительно `cd frontend`, затем `npm test` — 12 проверок контрактов, загрузки, серверного рендеринга пользователей и диалога, владения черновиком, точности ввода, URL, русских подписей, контраста и демоданных. Это не браузерные E2E-тесты.

Новые API-сценарии находятся в `tests/review-cases.mjs`: последовательный остаток между страницами, CSV/PDF по всем выбранным фильтрам, отсутствие секретов в пользователях и аудите, архивные ссылки, проверка дубликатов справочников, ошибки валидации без 500, многостраничный PDF и аудит изменения ролей. Финансовые записи и тестовые смены ролей создаются только в базе `_test`.

## Unit Tests

`dotnet test backend/tests/FaizaCash.UnitTests`

Изолированные xUnit-тесты Domain и Application не используют HTTP, EF Core и базу. Проверяют положительность суммы, предел numeric(18,2), отклонение лишних десятичных знаков, точность decimal, запрет перерасхода, расход ровно до нуля, хронологию и порядок проведения. Будущий приход не позволяет списывать средства задним числом. Проверяется также, что новая операция не делает отрицательным остаток последующей проведённой операции.

## Integration Tests

Сначала соберите сервер: `dotnet build backend/FaizaCash.sln`.

`node tests/integration.mjs --suite=integration`

Реальные API → EF Core → PostgreSQL: миграции, суммы, повторные запросы, параллельные расходы и проведение, сторно, отчётные итоги, CSV/PDF и аудит. Искусственный сбой вставки аудита должен откатить транзакцию, оставить документ черновиком и сохранить остаток.

## Security Tests

`node tests/security.mjs`

Проверяют анонимные запросы, роли, запрет повышения собственных прав, назначение касс только администратором, чужие кассы/документы/отчёты, владение черновиком, CSRF, ротацию и повторное использование refresh-токенов, выход. Проверки разрешённых действий кассира дополняют проверки запретов.

«Повторная регистрация» проверяется в двух смыслах: повторный логин пользователя (включая регистр, пробелы и одновременные запросы) и повторная регистрация операции по RequestKey. Публичного endpoint регистрации нет. Повтор с тем же ключом возвращает тот же документ, попытка заменить платёж с уже использованным ключом отклоняется.

## Окружение и результаты

Нужны .NET 10, Node.js, PostgreSQL и `psql`. Локальная конфигурация читается из игнорируемого `.runtime/local.json`. База определяется как отдельная база приложения с суффиксом `_test`; имя дополнительно проверяется перед очисткой. Проверки пересоздают только её схему. Рабочая база не очищается. Роль PostgreSQL должна владеть тестовой схемой. API тестов слушает порт 5081, рабочее приложение использует 5080. Подготовка администратора общая для интеграционного и security-наборов.

Наборы запускаются последовательно: `.runtime/database-tests.lock` предотвращает одновременную очистку общей схемы. При аварийном завершении сначала убедитесь, что тестовый процесс завершился, затем удаляйте оставшийся lock. Перед сборкой после изменения C# остановите свой локальный API, если Windows блокирует его DLL.

- Unit: `.runtime/unit-results/unit-tests.trx` при полном запуске.
- Integration: `.runtime/integration-test-results.json`.
- Security: `.runtime/security-test-results.json`.
- Совместимый общий API-прогон: `node tests/integration.mjs`, результат `.runtime/test-results.json`.

Security Tests — автоматизированные регрессионные проверки, они не заменяют независимый аудит или пентест. Проверки браузерного сценария и мобильной вёрстки остаются отдельной ручной задачей.
