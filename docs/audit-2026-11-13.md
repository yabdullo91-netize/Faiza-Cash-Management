## Подтверждённые проблемы

Ниже «подтверждено» означает доказательство в текущем коде/миграциях. Отдельно указано, что воспроизведено исполнением. HTTP-эксплуатация рабочего приложения не проводилась.

### 1. Высокая: обход изоляции касс через завершающий слеш

**Место:** backend/src/FaizaCash.Api/Middleware/AccessMiddleware.cs:27–31; Controllers/ApiEndpoints.cs:101, 116–125.

**Сценарий:** активный кассир или бухгалтер после смены первоначального пароля отправляет `GET /api/operations/` без cashboxId либо `GET /api/cashboxes/`.

**Доказательство:** обязательный cashboxId и выдача только назначенных касс реализованы через точное сравнение Path со строками без завершающего `/`. Для пути со слешем эти ветви не исполняются, box остаётся null, middleware передаёт запрос дальше. Обработчик операций при null cashboxId не ограничивает кассу; обработчик списка касс сам назначения не проверяет. При этом ASP.NET Core сопоставляет оба варианта пути с одним endpoint.

**Эксперимент:** отдельное минимальное приложение net10.0 без БД с тем же MapGet и сравнением пути: `/api/operations` → HTTP 200, ExactGuard=True; `/api/operations/` → HTTP 200, ExactGuard=False. Это воспроизводит механизм маршрутизации; раскрытие реальных данных не проверялось.

**Влияние:** чтение операций, сумм, оснований, авторов и контрагентов чужих касс через список; раскрытие списка всех касс. **Уверенность: высокая.**

**Исправление:** применять фильтр разрешённых касс непосредственно в запросах обработчиков/общем сервисе доступа. Не полагаться на строковое сравнение URL как единственную границу авторизации.

**Проверка:** интеграционные тесты admin/accountant/cashier с двумя кассами и отсутствующим назначением; оба варианта URL должны давать одинаковую изоляцию. Проверить варианты с регистром, параметрами и прямым id.

### 2. Высокая: проведение документа, изменённого после подтверждения пользователем

**Место:** frontend/src/app/App.jsx:94; components/OperationDialog.jsx:32,36; backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:159; Infrastructure/Services/LedgerService.cs:7–19,30.

**Сценарий:** A открывает подтверждение расхода 100 TJS. B меняет тот же draft на 1 000 TJS, увеличивая Version. A подтверждает увиденные 100 TJS. Клиент отправляет только id, сервер читает и проводит актуальные 1 000 TJS.

**Доказательство:** PATCH и DELETE сверяют переданный Version, а endpoint `/post` версии не принимает. FOR UPDATE защищает одновременную запись, но не связывает проведение с версией, которую видел пользователь.

**Влияние:** необратимое проведение суммы/реквизитов, которых пользователь не подтверждал. Проверка достаточности остатка остаётся действующей. **Уверенность: высокая, статический сценарий; HTTP-воспроизведение не выполнялось.**

**Исправление:** передавать expectedVersion при проведении и сравнивать под блокировкой, возвращая 409 при изменении. Обновлять карточку и запрашивать новое подтверждение.

**Проверка:** два сеанса: чтение v1 → изменение на v2 → проведение с v1 должно дать 409 и оставить draft/остаток неизменными; проведение с v2 — успешно.

### 3. Средняя: схема не защищает существенные связи и состояние документа

**Место:** backend/src/FaizaCash.Infrastructure/Persistence/CashDb.cs:28–34; Domain/Entities/Models.cs:13,18; Migrations/20261112052646_InitialLedger.cs:34–43,229–275.

**Доказательство:** Operations.CashboxId, DocumentTypeId, ReversalOfId/ReversalId, PostedBy не имеют соответствующих FK в начальной миграции; CashAccess имеет составной PK без FK на пользователя и кассу. Нет CHECK допустимых Status и обязательных реквизитов posted. Миграция ImmutableLedger запрещает изменение уже проведённой строки, но не делает перечисленные связи корректными при вставке/переходе из draft.

**Сценарий:** ошибочный скрипт импорта/обслуживания или будущий обработчик сохраняет операцию на несуществующую кассу либо posted без номера/даты проведения. Схема допускает это; запросы и отчёты становятся несогласованными.

**Влияние:** отсутствие последней линии защиты целостности финансового регистра. Обычный API проверяет часть реквизитов; прямой путь эксплуатации через него не доказан. Состояние реально развёрнутой схемы не проверено. **Уверенность: высокая относительно миграций.**

EF не обнаруживает отношения без навигаций только по имени скалярного поля: [официальная документация](https://github.com/dotnet/EntityFramework.Docs/blob/main/entity-framework/core/modeling/relationships/one-to-many.md).

**Исправление:** сначала проверить существующие данные, затем добавить явные отношения и согласованные CHECK. Не применять миграцию вслепую.

**Проверка:** на отдельной БД нарушения FK/posted должны отклоняться; допустимые draft, проведение и сторно — сохраняться.

### 4. Средняя: аудит выдачи доступа не позволяет установить, кому и к какой кассе выдан доступ

**Место:** backend/src/FaizaCash.Infrastructure/Persistence/CashDb.cs:14–19; Api/Controllers/ApiEndpoints.cs:185–186; Domain/Entities/Models.cs:18.

**Сценарий:** администратор назначает CashAccess. Запись сохраняется, но автоматический аудит не фиксирует UserId/CashboxId назначения: эти поля отсутствуют в whitelist изменений; у CashAccess нет Id, поэтому EntityId тоже null. Отдельное содержательное событие endpoint не создаёт.

**Влияние:** нельзя восстановить содержание изменения прав из аудита. Актор может быть известен через CurrentActor, но получатель и касса теряются. Аналогично автоматический аудит новой long-id сущности формируется до получения постоянного id; для справочников это ухудшает связь события с объектом. **Уверенность: высокая.**

**Исправление:** явное атомарное событие access_granted с безопасными идентификаторами актора, получателя и кассы; для универсального аудита корректно обрабатывать составные/генерируемые ключи.

**Проверка:** выдать два разных назначения и доказать, что каждое однозначно восстанавливается по журналу, без секретов.

### 5. Средняя: ключ идемпотентности не сравнивает вид документа

**Место:** backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:133–134; Application/DTOs/Projections.cs:3; frontend/src/components/OperationDialog.jsx:27.

**Сценарий:** повторить создание с тем же requestKey и остальными реквизитами, но другим допустимым documentTypeId. Сервер возвращает старый документ как успешный результат вместо конфликта отличающихся данных.

**Доказательство:** поле сохраняется при первом создании, но отсутствует в сравнении existing. View не возвращает DocumentTypeId; клиент формы всегда передаёт null, поэтому полноценного редактирования этого реквизита нет.

**Влияние:** успешный ответ может не соответствовать присланному содержимому. Дублирования суммы это само по себе не вызывает. **Уверенность: высокая.**

**Исправление:** включить поле в сравнение и DTO; отдельно решить, нужен ли его выбор в UI.

**Проверка:** одинаковый ключ и одинаковое тело возвращают тот же id; изменение только documentTypeId даёт 409.

### 6. Средняя: повторно напечатанный проведённый документ меняет реквизиты

**Место:** backend/src/FaizaCash.Api/Controllers/ApiEndpoints.cs:180–181; Controllers/ReportEndpoints.cs:59–64; Controllers/DirectoryEndpoints.cs:40–44.

**Сценарий:** провести операцию, выгрузить PDF, переименовать контрагента или организацию и повторить выгрузку. PDF получает текущие имена из справочника/Organizations, а не реквизиты на момент проведения.

**Влияние:** строка финансового регистра неизменна, но представление исторического документа меняется без сторно. Для учебного документа допустимость требует решения владельца; архивная воспроизводимость сейчас не обеспечена. **Уверенность: высокая по источникам данных PDF; сравнение двух PDF исполнением не проводилось.**

**Исправление:** если требуется историческая неизменность, сохранять снимок печатных реквизитов при проведении и печатать его. Установить отдельную политику отображения актуальных имён в обычных списках.

**Проверка:** PDF исторического документа сохраняет смысловые реквизиты после переименования справочников; сравнивать извлечённый текст, а не побайтовый файл с метаданными.

## Требует дополнительной проверки или решения

- **Compose и Origin:** nginx передаёт Host через `$host`, который не сохраняет внешний порт. При localhost:8080 и разрешённом Frontend:Origin для :5173 возможен 403 на login/refresh/logout. Это гипотеза конфигурации, контейнеры не запускались. Проверять фактические Origin/Host на отдельном Compose-развёртывании.
- **Согласованность отчёта при параллельном проведении:** строки, opening и итоги читаются отдельными запросами без общей snapshot-транзакции. При записи между запросами возможны разные срезы. Нужен конкурентный интеграционный тест; для экспорта отдельно проверить момент чтения opening/rows.
- **Производительность:** Post загружает весь проведённый регистр кассы и проверяет его под блокировкой кассы. Экспорты загружают все строки; CashCard делает отдельный запрос остатка на каждую кассу; справочники не имеют пагинации. Это наблюдаемые формы запросов, а не измеренная деградация. Требуются EXPLAIN ANALYZE и нагрузка с реалистичным объёмом. Индекс CashboxId/Date/PostingSeq уже есть; дополнительные индексы назначать после измерений.
- **Начальный остаток:** Balance учитывает Opening.Date <= date, а отчёт Opening — Date < from. Если существует отдельная Opening на первый день периода, результаты могут различаться. Обычный UI такую запись не создаёт; наличие исторических записей не проверено.
- **Отзыв доступа:** API умеет выдавать CashAccess, но не отзывать. Это подтверждённое функциональное ограничение, уже описанное в ТЗ; нужно решить обязательность. Отключение пользователя целиком не заменяет отзыв одной кассы.
- **Сессии:** refresh ротируется и хранится хешированным; access хранится в памяти клиента. Logout/смена пароля отзывают refresh, access живёт до истечения. Политика явно описана в README; немедленный отзыв всех access после смены пароля не реализован и требует решения.
- **Зависимости:** версии и lock-файлы просмотрены, актуальный CVE/advisory-анализ не выполнялся. Отсутствие уязвимостей не заявляется. Не проверены установленная версия PostgreSQL, Docker, TLS, reverse proxy, восстановление backup и production-конфигурация.
- **ТЗ устарело относительно кода:** раздел D-01 редакции 4.0 утверждает отсутствие строгой проверки сторно. В текущих Validate и LedgerService уже вызывается ReversalRules.MatchesOriginal и запрещено изменение финансовых реквизитов сторно. Старую формулировку нельзя переносить в список текущих дефектов. Нужна синхронизация документа с отдельным тестом; в рамках аудита документ не редактировался.
- **Объём диплома:** товары, смены/закрытие, вложения, импорт, XLSX и другие старые требования нельзя считать отменёнными только из-за отсутствия реализации. Редакция 4.0 имеет статус проекта, не утверждена.

## Архитектура и защитные свойства

Для текущего учебного масштаба четыре серверных проекта и разделённый React-клиент достаточны. Оснований добавлять микросервисы, CQRS или универсальный repository не обнаружено. Сосредоточенный ApiEndpoints и плотные однострочные обработчики усложняют обзор; переносить их стоит постепенно по функциям, вместе с тестами, без общего переписывания.

Полезные свойства текущего кода: decimal и numeric(18,2), запрет долей копейки, денежные JSON-строки, DateOnly и фиксированное время Душанбе; параметризованные SQL-блокировки; транзакция проведения вместе с аудитом; уникальный requestKey на автора; запрет повторного posted; проверка хронологического остатка; триггеры неизменности posted/audit; актуальность активности пользователя и снятых ролей проверяется по БД.

Авторизация мутаций повторно проверяется через ICashboxAccess; это не устраняет дефект GET-списков. Публичной регистрации и загрузки файлов не найдено. Динамическая конкатенация пользовательских значений в SQL в изученных обработчиках не обнаружена. React выводит текст штатным экранированием; явного dangerouslySetInnerHTML в изученных сценариях нет. CSV экранирует кавычки и опасное начало формул. CORS задаёт один Origin, auth-маршруты проверяют Origin и защитный заголовок при наличии cookie. Это результаты просмотра кода, а не полная гарантия защиты.

Автоматическое логирование исключений может включать детали ошибок провайдера; реальное содержимое журналов и права файлов не исследовались. Файлы секретов намеренно не открывались, поэтому отсутствие секретов во всей истории Git не подтверждено.

## Приоритетный план небольших исправлений

1. **Первая группа: изоляция GET-списков и регрессионные проверки URL со слешем.** Польза: закрыть подтверждённое раскрытие чужих касс. Риск: низкий/средний — важно сохранить доступ admin и допустимые фильтры.
2. **Отдельная группа: expectedVersion при проведении.** Польза: проводить именно подтверждённые реквизиты. Риск: средний — меняется контракт API/клиента; требуется совместное обновление и конкурентный тест.
3. **Идемпотентность и содержательный аудит прав.** Польза: точный контракт создания и расследуемость назначений. Риск: низкий/средний; изменения проверять отдельно.
4. **FK/CHECK после проверки данных на отдельной копии.** Польза: защита целостности. Риск: повышенный из-за возможных существующих несогласованностей; миграцию согласовать отдельно.
5. **По решению владельца:** снимок печатных реквизитов, отзыв доступа, утверждение объёма ТЗ; затем контейнерная, браузерная и нагрузочная приёмка.

Предлагаю одобрить только первую группу: исправление изоляции списков касс/операций и тесты обхода через завершающий слеш. До отдельного разрешения исправления не выполняются.
